================================================================================
1. VISÃO GERAL E DIAGNÓSTICO DO PROJETO
================================================================================

O NexusClass é uma aplicação de alta riqueza funcional: conta com autenticação,
gestão de papéis (Aluno, Professor, Master), calendário de compromissos, mural de
avisos, entregas de atividades, chat em tempo real e um assistente inteligente
baseado no Google Gemini que executa Function Calling.

Diagnóstico de Engenharia de Software:
- PONTOS FORTES:
  * Organização modular por domínio em `src/hooks/` (ex: MuralHooks, CalendarioHooks, botsHooks).
  * Uso consistente de TypeScript com interfaces e tipos dedicados.
  * Componentização visual avançada com Radix e Tailwind.

- OPORTUNIDADES DE MELHORIA ARQUITETURAL:
  * Acoplamento Direto: Múltiplos hooks realizam queries diretas com o cliente do
    Supabase (PostgREST queries), dificultando testes unitários sem mockar todo o SDK.
  * Ausência de Suíte de Testes Automatizados configurada no pipeline (CI/CD).
  * Regras de IA acopladas ao SDK concreto da Google no chat, dificultando
    troca de provedores ou execução offline de testes.

2. MODELOS DE TESTES AUTOMATIZADOS (PIRÂMIDE DE TESTES)
================================================================================

Na Engenharia de Software moderna, adotamos a Pirâmide de Testes (Mike Cohn):
uma base sólida de testes rápidos e baratos (Unitários), camada intermediária de
integração e um topo enxuto de testes de ponta a ponta (E2E).

       /\
      /  \        [E2E: Playwright] - Fluxos Críticos
     /----\       [Integração: Vitest + MSW] - Hooks e Comunicação de Módulos
    /------\      [Unitários: Vitest] - Funções Puras, Utilitários e Parsers
   /________\

--------------------------------------------------------------------------------
2.1. TESTES UNITÁRIOS (UNIT TESTS)
--------------------------------------------------------------------------------
- OBJETIVO: Validar funções puras, cálculos, formatações e regras de negócio
  sem dependência de banco de dados, rede ou DOM.
- FERRAMENTA RECOMENDADA: Vitest.
- ALVOS NO NEXUSCLASS:
  * `src/lib/utils.ts`:
    - `formatarErroSupabase()`: testar retorno para códigos 'PGRST205', '42P01', '42501'.
    - `getCorMateria()` e `getCorNomeUsuario()`: testar consistência do algoritmo de hash.
    - `comparaDataHj()`, `isDataEntregaFutura()`, `montarDataEvento()`.
    - `extrairUrlsAnexo()` e `obterNomeArquivoDoUrl()`.
  * `src/lib/assetPath.ts`:
    - Resolução de URLs de assets estáticos em ambientes de produção vs desenvolvimento.

--------------------------------------------------------------------------------
2.2. TESTES DE INTEGRAÇÃO (INTEGRATION TESTS)
--------------------------------------------------------------------------------
- OBJETIVO: Testar a integração entre componentes de interface (React), hooks
  customizados e chamadas de API simuladas com mocks confiáveis.
- FERRAMENTAS RECOMENDADAS: React Testing Library + MSW (Mock Service Worker).
- ALVOS NO NEXUSCLASS:
  * `useCalendario`: verificar se o hook emite estado de "carregando", filtra
    eventos expirados (`eventoAindaAtivo`) e trata adequadamente erros de RLS.
  * `BoxAgendamento.tsx`: simular o preenchimento do formulário de agendamento e
    verificar se a ação de submit despacha a chamada correta para o serviço.
  * `ChatBot.tsx` + `useChatBot`: simular mensagem do usuário e resposta mockada
    do assistente com disparo de Function Calling.

--------------------------------------------------------------------------------
2.3. TESTES DE PONTA A PONTA (END-TO-END / E2E)
--------------------------------------------------------------------------------
- OBJETIVO: Executar o software em um navegador real automatizado, simulando o
  comportamento do usuário final do início ao fim.
- FERRAMENTA: Playwright (já presente em `package.json`).
- CENÁRIOS CRÍTICOS NO NEXUSCLASS:
  1. Fluxo de Autenticação:
     - Usuário acessa `/login`, preenche credenciais válidas e é redirecionado.
     - Usuário não autenticado tenta acessar rota protegida (`ProtectedRoute`) e é
       barrado.
  2. Fluxo de Criação e Entrega de Atividade:
     - Professor cria uma atividade na turma.
     - Aluno visualiza a atividade pendente, envia arquivo de resposta e confirma entrega.
  3. Fluxo de Agendamento no Calendário:
     - Usuário clica em uma data, abre o modal de agendamento, salva evento e
       vê o evento refletido no calendário e na lista de compromissos.

--------------------------------------------------------------------------------
2.4. TESTES DE REGRESSÃO VISUAL E ACESSIBILIDADE
--------------------------------------------------------------------------------
- OBJETIVO: Garantir que alterações no Tailwind ou componentes Shadcn não quebrem
  o layout em Dark/Light mode ou violem diretrizes WCAG (a11y).
- FERRAMENTAS: Playwright Visual Comparisons (`toHaveScreenshot`) + axe-core.

--------------------------------------------------------------------------------
3.1. PADRÕES CRIACIONAIS (CREATIONAL PATTERNS)
--------------------------------------------------------------------------------
1. FACTORY METHOD (FÁBRICA DE NOTIFICAÇÕES / EVENTOS):
   * Onde aplicar: Módulo de Notificações e Atividades.
   * Finalidade: Criar objetos de evento/notificação padronizados (ex: NotificacaoMensagem,
     NotificacaoEntrega, NotificacaoAviso) a partir de uma interface comum.

2. SINGLETON:
   * Onde aplicar: Cliente Supabase (`src/lib/supabaseClient.ts`) e Gerenciador de Áudio (`Howler`).
   * Finalidade: Garantir uma única instância compartilhada de conexões e recursos.

--------------------------------------------------------------------------------
3.2. PADRÕES ESTRUTURAIS (STRUCTURAL PATTERNS)
--------------------------------------------------------------------------------
3. REPOSITORY PATTERN / SERVICE LAYER (DETALHADO NA SEÇÃO 4):
   * Onde aplicar: Toda a comunicação com Supabase (Calendario, Mural, Turmas, Dúvidas).
   * Finalidade: Isolar a persistência de dados da camada de apresentação/hooks.

4. ADAPTER PATTERN (ADAPTADOR DE IA / SERVIÇOS EXTERNOS):
   * Onde aplicar: `src/hooks/botsHooks/`.
   * Finalidade: Criar uma interface `IAssistantService` para que a aplicação não dependa
     diretamente das classes proprietárias do Google Generative AI SDK.

5. FAÇADE (FACHADA):
   * Onde aplicar: Módulo de inicialização e sincronização offline com LocalStorage.
   * Finalidade: Oferecer uma API unificada e simplificada para cache local e sincronização.

--------------------------------------------------------------------------------
3.3. PADRÕES COMPORTAMENTAIS (BEHAVIORAL PATTERNS)
--------------------------------------------------------------------------------
6. COMMAND PATTERN (COMANDOS DO CHATBOT - DETALHADO NA SEÇÃO 4):
   * Onde aplicar: Function Calling das ferramentas do Bot (`configBot.ts`).
   * Finalidade: Encapsular cada ferramenta da IA como um comando executável autônomo.

7. STRATEGY PATTERN (ESTRATÉGIA DE AUTORIZAÇÃO / RBAC):
   * Onde aplicar: Controle de acesso (`role: 'aluno' | 'professor' | 'master'`).
   * Finalidade: Definir estratégias polimórficas de visualização e permissão de ações.

8. OBSERVER PATTERN (OBSERVADOR / PUB-SUB):
   * Onde aplicar: `src/components/Mensagens.tsx` e atualizações do Mural em tempo real.
   * Finalidade: Subscrever múltiplos componentes a canais de eventos do Supabase Realtime.

--------------------------------------------------------------------------------
3.4. PADRÕES ESPECÍFICOS PARA REACT/FRONTEND
--------------------------------------------------------------------------------
9. COMPOUND COMPONENTS PATTERN:
   * Onde aplicar: `TurmaCard`, `BoxEntregaAtividade` e Diálogos modais.
   * Finalidade: Permitir composição declarativa de interfaces (`<TurmaCard.Header />`, etc.).

10. CUSTOM HOOK PATTERN (já utilizado no projeto):
    * Onde aplicar: Separação de estado reativo e efeitos da renderização JSX.

4.1. ESTUDO DE CASO 1: REPOSITORY PATTERN + INVERSÃO DE DEPENDÊNCIA (DIP)
--------------------------------------------------------------------------------

CONTEXTO TEÓRICO (SOLID - Dependency Inversion Principle):
"Módulos de alto nível não devem depender de módulos de baixo nível.
Ambos devem depender de abstrações."

NO NEXUSCLASS ATUALMENTE:
O hook `useCalendario.ts` realiza consultas diretamente no Supabase:

  useCalendario.ts ---> Supabase Client (PostgREST SDK)

PROBLEMAS DESTA ABORDAGEM:
1. Impossível testar a lógica do hook sem subir um banco ou mockar dezenas de
   funções internas encadeadas (`.from().select().gte().or().order()`).
2. Se a tabela mudar de nome ou se migrarmos para outro backend, todo o código de UI
   precisa ser refatorado.
3. Viola o Princípio da Responsabilidade Única (SRP): o hook gerencia estado de UI E
   conhece a sintaxe de query SQL/PostgREST.

ARQUITETURA PROPOSTA COM REPOSITORY PATTERN:

  +-----------------------+
  |  Componentes / Hooks  |  (Camada de Apresentação)
  |   (useCalendario)     |
  +-----------------------+
              |
              v (Consome)
  +-----------------------------------+
  |   <<interface>>                   |  (Abstração / Contrato)
  |   ICalendarioRepository           |
  +-----------------------------------+
        ^                       ^
        | (Implementa)          | (Implementa)
  +--------------------+   +----------------------+
  | SupabaseCalendario |   | MockCalendarioRepo   |
  | Repository         |   | (Para Testes Rápidos)|
  +--------------------+   +----------------------+
        |
        v
    Supabase DB

Passo 1: Definir a Interface do Repositório (`src/repositories/ICalendarioRepository.ts`)
--------------------------------------------------------------------------------
export interface NovoEventoDTO {
  titulo: string;
  descricao: string;
  data: string;
  horario?: string;
  tipo: "pessoal" | "turma";
  turma_id?: string;
  autor_id: string;
}

export interface ICalendarioRepository {
  listarEventosFuturos(usuarioId: string, role: string, turmasIds: string[]): Promise<EventoCalendario[]>;
  salvarEvento(evento: NovoEventoDTO): Promise<EventoCalendario>;
  excluirEvento(eventoId: string): Promise<void>;
}

Passo 2: Implementação Concreta com Supabase (`src/repositories/SupabaseCalendarioRepository.ts`)
--------------------------------------------------------------------------------
import { supabase } from "@/lib/supabaseClient";
import { paraChaveData, hojeLocal } from "@/lib/utils";
import type { ICalendarioRepository, NovoEventoDTO } from "./ICalendarioRepository";

export class SupabaseCalendarioRepository implements ICalendarioRepository {
  async listarEventosFuturos(usuarioId: string, role: string, turmasIds: string[]): Promise<EventoCalendario[]> {
    if (!supabase) throw new Error("Supabase não configurado.");

    let query = supabase
      .from("eventos_calendario")
      .select("id,titulo,descricao,data,horario,tipo,turma_id,autor_id")
      .gte("data", paraChaveData(hojeLocal()));

    if (role !== "master") {
      if (turmasIds.length > 0) {
        query = query.or(`and(tipo.eq.pessoal,autor_id.eq.${usuarioId}),and(tipo.eq.turma,turma_id.in.(${turmasIds.join(",")}))`);
      } else {
        query = query.eq("tipo", "pessoal").eq("autor_id", usuarioId);
      }
    }

    const { data, error } = await query.order("data", { ascending: true });
    if (error) throw error;
    return data || [];
  }

  async salvarEvento(evento: NovoEventoDTO): Promise<EventoCalendario> {
    if (!supabase) throw new Error("Supabase não configurado.");
    const { data, error } = await supabase.from("eventos_calendario").insert(evento).select().single();
    if (error) throw error;
    return data;
  }

  async excluirEvento(eventoId: string): Promise<void> {
    if (!supabase) throw new Error("Supabase não configurado.");
    const { error } = await supabase.from("eventos_calendario").delete().eq("id", eventoId);
    if (error) throw error;
  }
}

Passo 3: Mock em Memória para Testes Unitários (`src/repositories/MockCalendarioRepository.ts`)
--------------------------------------------------------------------------------
export class MockCalendarioRepository implements ICalendarioRepository {
  private eventos: EventoCalendario[] = [];

  async listarEventosFuturos(): Promise<EventoCalendario[]> {
    return [...this.eventos];
  }

  async salvarEvento(evento: NovoEventoDTO): Promise<EventoCalendario> {
    const novo: EventoCalendario = { id: String(Date.now()), ...evento, horario: evento.horario || "" };
    this.eventos.push(novo);
    return novo;
  }

  async excluirEvento(eventoId: string): Promise<void> {
    this.eventos = this.eventos.filter(e => e.id !== eventoId);
  }
}

Passo 4: Hook useCalendario Consumindo o Repositório (Injeção de Dependência)
--------------------------------------------------------------------------------
export function useCalendario({
  perfil,
  inscricoes,
  repository = new SupabaseCalendarioRepository() // Injeção de dependência com default
}: UseCalendarioProps & { repository?: ICalendarioRepository }) {
  const [eventos, setEventos] = useState<EventoCalendario[]>([]);
  const [carregando, setCarregando] = useState(false);

  const carregar = useCallback(async () => {
    if (!perfil?.id) return;
    setCarregando(true);
    try {
      const turmasIds = Object.keys(inscricoes || {}).filter(k => inscricoes[k]);
      const dados = await repository.listarEventosFuturos(perfil.id, perfil.role, turmasIds);
      setEventos(dados);
    } catch (err: any) {
      console.error(err);
    } finally {
      setCarregando(false);
    }
  }, [perfil, inscricoes, repository]);

  return { eventos, carregando, carregar };
}

CONTEXTO NO PROJETO:
O arquivo `src/hooks/botsHooks/configBot.ts` define Function Calling para o Gemini:
- `obterEventosCalendario`
- `obterDuvidasEstudante`
- `obterAtividadesAbertas`
- `obterPostsProfessor`

APLICAÇÃO DO COMMAND PATTERN:
Cada função executada pela IA torna-se um Comando independente:

```typescript
export interface IBotToolCommand {
  readonly name: string;
  readonly description: string;
  readonly schema: any;
  execute(args: any, context: ExecutionContext): Promise<any>;
}

export class ObterEventosCalendarioCommand implements IBotToolCommand {
  readonly name = "obterEventosCalendario";
  readonly description = "Retorna os próximos eventos do usuário";
  readonly schema = { type: SchemaType.OBJECT, properties: {} };

  async execute(args: any, context: ExecutionContext) {
    return context.calendarioRepo.listarEventosFuturos(context.userId, context.role, context.turmas);
  }
}
```

VANTAGENS:
- Princípio Aberto/Fechado (OCP): para adicionar uma nova ferramenta (ex: "obterNotasAluno"),
  cria-se uma nova classe de comando sem alterar o código existente do ChatBot.
- Testabilidade: cada comando pode ser testado unitariamente de forma 100% isolada.
